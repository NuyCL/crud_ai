# Step 8: วิเคราะห์ก่อนแปล (ภาษาปลายทางละ 1 รอบ)

> ⏳ **ฉบับร่าง:** ยังไม่มี `go/` ให้วิเคราะห์จริง ตัวอย่างความเสี่ยงด้านล่างเป็นการคาดการณ์จากธรรมชาติของภาษา ไม่ใช่ผลจากรายงานที่ AI ทำจริง

**เป้าหมาย:** ก่อนเขียนโค้ดภาษาใหม่ ให้ AI ทำรายงานว่า "อะไรใน Go ที่แปลตรงๆ ไม่ได้" และคุณอนุมัติแผนนั้นก่อน
**เวลา:** 20 นาทีต่อภาษา · **ก่อนหน้า:** [Step 7](07-skills.md) · **ถัดไป:** [Step 9](09-port-typescript.md)

## ทำไมต้องวิเคราะห์ก่อน

AI ที่ได้รับคำสั่งว่า "แปล Go เป็น Rust" จะเริ่มแปลบรรทัดต่อบรรทัดทันที แล้วไปติดปัญหากลางทาง (เช่น ownership ของ database connection) และแก้แบบเฉพาะหน้า รายงานก่อนแปลบังคับให้ปัญหาเหล่านี้ถูกคิดและตัดสินใจ **ในที่ที่คุณมองเห็น** และเป็นเอกสารที่ใช้เทียบหลังแปลว่าคาดถูกแค่ไหน

## ขั้นตอน

### 8.1 รัน prompt (เปลี่ยน `<lang>` เป็น typescript, python, java หรือ rust)

```text
เราจะแปล go/ เป็น <lang> อ่าน go/ ทั้งหมด, CONVENTIONS.md, spec/ แล้วเขียน docs/porting/<lang>-analysis.md
"ห้ามเขียนโค้ดแปล" ในรายงานต้องมี:

1. ตาราง "ส่วนของ Go ที่ใช้จริง -> วิธีใน <lang>" ครอบคลุมทุกอย่างที่ใช้ใน go/ (error handling,
   struct/pointer, interface, goroutine/mutex ถ้ามี, JSON, database, HTTP routing, test) อ้าง file:line ของต้นฉบับ
2. กับดักด้านตัวเลขและข้อความของ <lang> ที่กระทบสเปกนี้: integer wrap 32 บิต, UTF-8 vs UTF-16/rune,
   ชนิดตัวเลขของ JSON (10 กับ 10.5), null vs ไม่ส่ง vs 0/false, การเทียบ "1" กับ 1 และ true กับ 1
3. library ที่จะใช้ (เฉพาะที่อยู่ใน CONVENTIONS.md) ถ้าต้องการนอกรายการ ให้ระบุเหตุผลเป็นข้อยกเว้นรอฉันอนุมัติ
4. framework ทำอะไรให้เองที่ "ขัดกับสเปก" เช่น รูปแบบ error เริ่มต้น, status code ของ validation (422 vs 400),
   การแปลงชนิดอัตโนมัติ ("50" -> 50) และวิธีปิด/แทนที่
5. ความเสี่ยง 5 อันดับแรก เรียงตามผลกระทบ พร้อมบอกว่า vectors หรือ contract test ข้อไหนจะจับได้
6. ลำดับ layer และคำสั่ง gate ของ layer แต่ละชั้น
7. คำถามที่ต้องให้ฉันตัดสินใจ (ถ้ามี)
```

### 8.2 ตัวอย่างที่ควรเห็นในรายงาน (TypeScript, คาดการณ์)

| ประเด็น | ทำไมสำคัญ | ตัวจับ |
|---|---|---|
| ตัวเลขทุกตัวเป็น double | คูณ FNV ด้วย `*` ได้ผลเพี้ยน ต้องใช้ `Math.imul(...) >>> 0` | `fnv1a32.json` |
| `string.length` เป็น UTF-16 unit | description emoji 500 ตัว ถูกนับเป็น 1000 | test "500 emoji" |
| hash ต้องบน UTF-8 | `charCodeAt` ได้ UTF-16, ต้อง `Buffer.from(s, "utf8")` | `bucketing.json` (userId ไทย/emoji) |
| framework แปลง/ปฏิเสธ body เอง | รูปแบบ error ไม่ตรง `{"error":{"code","message"}}` | validation tests |
| `{}` มี prototype | attribute ชื่อ `__proto__` หรือ `constructor` อาจหลุดเข้า rule | ต้องเพิ่ม vector ถ้าสเปกเรื่องนี้ชัดเจน |
| `==` กับ `typeof` | `"1" == 1` เป็น true ใน JS | `target-eq-type-*` |

### 8.3 คนอนุมัติ (gate สำคัญของ step นี้)

- [ ] ตารางข้อ 1 ครอบคลุมทุกอย่างที่ `go/` ใช้จริง ลองสุ่มเปิด 3 ไฟล์ใน `go/` แล้วหาว่ามีในตารางไหม
- [ ] ข้อ 2 พูดถึงทั้งตัวเลข **และ** ข้อความ/Unicode
- [ ] ข้อ 4 ระบุ framework ที่เลือกว่าทำอะไร "เอง" ที่ขัดกับสเปก และมีวิธีแก้ (ถ้าไม่มี รายงานอาจยังไม่ได้ลงรายละเอียด)
- [ ] ความเสี่ยงแต่ละข้อมีตัวจับ (test) ถ้ามีข้อที่ **ไม่มีตัวจับ** ให้เพิ่ม vector หรือ contract test **ก่อน** แปล (กลับไป step 4/5)
- [ ] ไม่มีไลบรารีนอกรายการ หรือมีแต่คุณอนุมัติแล้ว

```text
ข้อ <ระบุ> ยังไม่ชัด/ไม่มีตัวจับ ปรับรายงานแล้วบอกว่าต้องเพิ่ม test อะไรใน tests/ (ยังไม่ต้องเพิ่มเอง)
```

เมื่อพอใจ:

```bash
git add -A && git commit -m "Add <lang> porting analysis"
```

## ตรวจผล

```bash
test -s docs/porting/<lang>-analysis.md && grep -c "^|" docs/porting/<lang>-analysis.md
```

ผลที่ถูกต้อง: มีไฟล์และมีตารางหลายแถว (รายงานที่ไม่มีตารางมักเป็นข้อความกว้างๆ)

## ข้อควรระวัง

- รายงานที่ฟังดูฉลาดแต่ไม่อ้าง `file:line` ของต้นฉบับ คือรายงานที่ AI ยังไม่ได้อ่านโค้ดจริง ให้สั่งทำใหม่
- ถ้าข้อ 4 บอกว่า "framework จัดการให้อยู่แล้ว" ให้ท้าทาย: framework จัดการ **ตามค่าเริ่มต้นของมัน** ซึ่งมักไม่ใช่ตามสเปกของเรา (เช่น 422 แทน 400)
- เก็บรายงานไว้ใช้ตอน step 12: เทียบว่าความเสี่ยงที่ทำนายไว้เกิดจริงกี่ข้อ และมีอะไรที่ไม่ได้ทำนายไว้
