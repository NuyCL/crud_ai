# Step 12: สรุปบทเรียน (ทำให้รอบหน้าเร็วขึ้นและดีขึ้น)

> ⏳ **ทำไปบางส่วน:** บทเรียนต่อภาษามีครบแล้ว — [`typescript.md`](../../../lessons/typescript.md), [`python.md`](../../../lessons/python.md), [`java.md`](../../../lessons/java.md), [`rust.md`](../../../lessons/rust.md), [`sdk-js.md`](../../../lessons/sdk-js.md) — พร้อมตารางเปรียบเทียบ [`comparison.md`](../../../lessons/comparison.md) (ตัวเลขทุกตัวมาจากการรันจริง; เวลาไม่ได้บันทึก) ที่ **ยังไม่ได้ทำ:** `lessons/summary.md` ตามขั้น 12.3 (สังเคราะห์แผนเทียบจริง/ความเสี่ยงที่ทำนายแล้วเกิดจริง), การปรับ `CLAUDE.md`/skill ตามข้อเสนอในบทเรียน (รอผู้ใช้อนุมัติ), และการให้คนอื่นลองทำตามเอกสารเพื่อตอบเกณฑ์ข้อ 4

**เป้าหมาย:** เปลี่ยนประสบการณ์เป็นของที่ใช้ซ้ำได้: บทเรียนต่อภาษา, prompt/skill ที่ปรับแล้ว, และข้อสรุปว่า strategy "สเปก + test กลาง" ได้ผลแค่ไหน
**เวลา:** 20 นาที · **ก่อนหน้า:** [Step 11](11-js-sdk.md) · จบ

## ทำไมต้องมีขั้นนี้

วัตถุประสงค์ข้อ 3 ของโปรเจกต์คือ "strategy ของการแปลที่ **ensure quality ได้**" ถ้าไม่เก็บข้อมูลว่า gate ไหนจับ bug อะไร และ AI พลาดอะไรซ้ำๆ คุณจะมีแค่ความรู้สึก ไม่ใช่ strategy

## ขั้นตอน

### 12.1 เก็บตัวเลขจากประวัติจริง

```bash
git log --oneline --reverse | grep -iE "port|TypeScript|Python|Java|Rust"   # commit ต่อ layer
git log --stat --format='%h %s' -- tests spec | head -40                      # ครั้งไหนที่แตะ spec/tests (ควรมีน้อยและมีเหตุผล)
```

ตอบให้ได้ต่อภาษา: ต้องแก้กี่รอบถึงผ่าน gate ของแต่ละ layer, gate ไหนจับ bug (vectors / unit / contract / diff review), มี bug กี่ข้อที่หลุดไปถึง contract test ทั้งที่ unit test ผ่าน

### 12.3 ให้ AI ช่วยสังเคราะห์ (คุณเป็นคนตัดสินว่าข้อสรุปไหนจริง)

```text
อ่าน lessons/*.md, docs/plan.md, docs/porting/*-analysis.md และ git log แล้วเขียน lessons/summary.md:
1. แผนใน docs/plan.md ต่างจากที่ทำจริงตรงไหน (ตาราง: แผน / จริง / สาเหตุ)
2. bug ที่เกิดซ้ำในหลายภาษา -> ต้นเหตุร่วมอยู่ที่สเปก, test หรือ prompt?
3. ความเสี่ยงที่ทำนายไว้แล้วเกิดจริง / ไม่เกิด / เกิดแต่ไม่ได้ทำนาย
4. gate ไหนคุ้มที่สุด (จับ bug ได้มากต่อเวลาที่ใช้) และไหนที่ไม่เคยจับอะไรเลย
5. ข้อเสนอแก้ CONVENTIONS.md, skills และ prompts พร้อมเหตุผล (เสนออย่างเดียว ยังไม่แก้)
อ้างหลักฐาน (ไฟล์/commit) ทุกข้อ ข้อไหนไม่มีหลักฐานให้ระบุว่าเป็นข้อสันนิษฐาน
```

### 12.4 ปรับเครื่องมือตามข้อเสนอที่คุณเห็นด้วย

- ข้อผิดพลาดที่เกิดจากสเปกกำกวม → แก้ `spec/` + เพิ่ม vector/test (กลับไป step 2–5)
- ข้อผิดพลาดที่ AI ทำซ้ำ → เพิ่มลง `CLAUDE.md` หรือ skill เป็น "ห้าม/ต้อง" ที่เฉพาะเจาะจง (อย่าเขียนกว้างๆ ว่า "ระวังให้มาก")
- gate ที่ไม่เคยจับอะไร → พิจารณาตัดออกเพื่อลดเวลา หรือทำ mutation check ว่ามันใช้ได้จริงไหม

```bash
git add -A && git commit -m "Add lessons and update conventions"
```

## เกณฑ์ว่า "strategy ได้ผล"

ตอบ 5 ข้อนี้ด้วยข้อมูล ไม่ใช่ความรู้สึก:

1. ภาษาใหม่ผ่าน contract test **โดยไม่แก้ test** ใช่หรือไม่?
2. bug ที่สำคัญ (integer, Unicode, ชนิดข้อมูล) ถูกจับโดย **vectors ก่อนถึง HTTP** กี่เปอร์เซ็นต์?
3. ภาษาที่ 2–4 ใช้เวลา/รอบแก้ **น้อยลง** กว่าภาษาแรกหรือไม่ (บทเรียนส่งต่อได้จริง)?
4. dev คนใหม่ที่ไม่เคยเห็นโปรเจกต์ทำตามเอกสารชุดนี้แล้วถึงผลเดียวกันหรือไม่? (ลองกับ 1 คน)
5. มีสิ่งที่ผ่านทุก gate แต่ผู้ใช้เห็นว่า **ผิด** หรือไม่? ถ้ามี ต้องเพิ่ม gate ชนิดใหม่

## ข้อควรระวัง

- บันทึกทันทีหลังจบแต่ละภาษา ไม่ใช่ตอนจบทั้งหมด ความทรงจำเรื่อง "รอบที่แล้ว AI พลาดอะไร" หายเร็ว
- บันทึก **ความล้มเหลวด้วย** เช่น prompt ที่ไม่ได้ผล ซึ่งมีค่าไม่น้อยกว่าที่ได้ผล
- อย่าสรุปว่า "AI ดี/ไม่ดี" สรุปให้เป็น "ขั้นตอนไหนไว้ใจได้ ขั้นตอนไหนต้องมีคนตรวจ"
