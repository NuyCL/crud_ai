# Step 1: ขอแผนจาก AI

**เป้าหมาย:** ได้แผนที่ตกลงกันแล้ว ก่อนที่ AI จะเขียนอะไรสักบรรทัด: ลำดับงาน ของที่ต้องได้ในแต่ละขั้น คำสั่งตรวจ ความเสี่ยง และคำถามที่ต้องตอบ
**เวลา:** 20 นาที · **ก่อนหน้า:** [Step 0](00-setup.md) · **ถัดไป:** [Step 2](02-spec-rules.md)

## ทำไมต้องวางแผนก่อน

ถ้าสั่ง "ทำ feature flag service" ตรงๆ AI จะเลือกให้ทุกอย่าง (database, โครงสร้าง, ภาษาของ test) และเขียนโค้ดจำนวนมากที่ตรวจยาก การขอ **แผนก่อน** ทำให้คุณเห็นการตัดสินใจเหล่านั้นและเปลี่ยนได้ในราคาถูก

## ขั้นตอน

### 1.1 ใส่โจทย์ให้ AI

สร้างไฟล์ `README.md` สั้นๆ ที่บอกโจทย์ (หรือคัดจากบทสรุปโปรเจกต์ของคุณ) อย่างน้อยต้องมี:

```markdown
# Feature Flag Service
- MVP1: เปิด/ปิด feature (on/off)
- MVP2: A/B testing
- MVP3: JavaScript library สำหรับ web
- เขียนต้นฉบับด้วย Go แล้วให้ AI แปลเป็น TypeScript, Python, Java, Rust
- เป้าหมาย: ฝึกหลายภาษา, ฝึกวางขั้นตอนใช้ AI แปลโค้ด, หา strategy ที่การันตีคุณภาพได้
```

### 1.2 รัน prompt ขอแผน (ใช้ plan mode ถ้ามี: กด `Shift+Tab` ใน Claude Code)

```text
ฉันจะทำ workshop สอน dev ใช้ AI สร้างและแปลโค้ดระหว่างภาษา โดยใช้ feature flag service
เป็นโจทย์ อ่าน README.md และ CLAUDE.md ก่อน แล้ว "ยังไม่ต้องเขียนโค้ดหรือสร้างไฟล์" ให้ทำดังนี้:

1. แบ่งงานเป็น step เรียงตามลำดับ แต่ละ step ระบุ: เป้าหมาย, ไฟล์ที่ได้, คำสั่งที่รันตรวจว่าเสร็จ
2. ระบุจุดที่ "คน" ต้องตัดสินใจเองก่อนให้ AI ทำต่อ
3. ระบุความเสี่ยง 5 อันดับแรก (โดยเฉพาะตอนแปลภาษา) พร้อมวิธีลดความเสี่ยงแต่ละข้อ
4. ถามคำถามที่ถ้าไม่ตอบแล้วแผนจะเปลี่ยน ไม่เกิน 7 ข้อ

ตอบเป็นภาษาไทย ใช้ตารางสำหรับแผน
```

### 1.3 รีวิวแผนด้วยเช็กลิสต์นี้

- [ ] **ทุก step มีคำสั่งตรวจ** ที่รันได้จริง (ไม่ใช่ "ตรวจว่าถูกต้อง")
- [ ] **สเปกและ test มาก่อนโค้ด** ถ้า AI เสนอให้เขียนโค้ดก่อน ให้สั่งแก้
- [ ] มี **test กลางที่ไม่ผูกกับภาษา** เพื่อใช้ตัดสินทุกภาษา (ถ้าไม่มี การแปลจะเทียบกันไม่ได้)
- [ ] ความเสี่ยงมีตัวเลข/จำนวนเต็มล้น, ข้อความ Unicode, การเทียบชนิดข้อมูล (ถ้าไม่เจอ ให้ถามว่า "แล้วเรื่อง integer overflow ในแต่ละภาษาล่ะ")
- [ ] ไม่มี step ที่ใหญ่เกิน 90 นาที ถ้ามี ให้สั่งแบ่ง

### 1.4 ตอบคำถามของ AI แล้วบันทึกเป็น `docs/plan.md`

คำถามที่มักโผล่และคำตอบที่แนะนำสำหรับ workshop:

| คำถาม | แนะนำ | เหตุผล |
|---|---|---|
| ใช้ database อะไร | SQLite | ไม่ต้องติดตั้ง ทุกภาษามี driver |
| Evaluate ฝั่ง server หรือ client | ฝั่ง server ก่อน | ลดพื้นที่ที่ต้องแปลซ้ำ และปลอดภัยกว่า |
| มี admin UI ไหม | ไม่มี ใช้ API + curl | โฟกัสที่การแปลโค้ด |
| เริ่มภาษาไหนก่อน | Go แล้ว TypeScript | TypeScript ใกล้ Go ที่สุดในแง่ HTTP/JSON เห็นหลักการได้เร็ว |
| ภาษาไหนท้ายสุด | Rust | ownership ต่างจาก Go มากสุด |

```text
บันทึกแผนที่ตกลงกันเป็น docs/plan.md โดยรวมคำตอบของฉันข้างบนเข้าไปในส่วน "Decisions"
อย่าแก้ข้อมูลอื่น
```

```bash
git add -A && git commit -m "Add agreed plan"
```

## ตรวจผล

```bash
test -s docs/plan.md && grep -c "^|" docs/plan.md
```

ผลที่ถูกต้อง: ไฟล์มีเนื้อหา และมีแถวตารางหลายแถว (แผนอยู่ในรูปตาราง) และส่วน "Decisions" ครบทุกคำถามที่ AI ถาม

## เฉลย/อ้างอิงในรีโปนี้

- แผนภาพรวมที่ได้จากการทำจริง: [`README.md`](../../../README.md) หัวข้อ "Pipeline การใช้ AI" และ "แผน Workshop"
- Decisions ที่ใช้: SQLite, evaluate ฝั่ง server, ไม่มี admin UI (ระบุไว้ในหัวข้อ "Decisions เบื้องต้น")

## ข้อควรระวัง

- **อย่ากดอนุมัติแผนโดยไม่อ่าน** แผนที่ฟังดูดีแต่ไม่มีคำสั่งตรวจ จะกลายเป็นงานที่ตรวจไม่ได้ทุก step
- ถ้าแผนยาวเกินไป ให้สั่ง "สรุปแผนเหลือ 1 หน้า" แล้วเก็บฉบับเต็มไว้อ้างอิง
- แผนไม่ใช่สัญญา: เมื่อทำจริงแล้วเจอสิ่งที่ผิดคาด ให้กลับมาแก้ `docs/plan.md` ด้วย (ใน step 12 จะใช้ไฟล์นี้เทียบแผนกับของจริง)
