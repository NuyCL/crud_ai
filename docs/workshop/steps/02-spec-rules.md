# Step 2: สเปกกติกา (ให้ AI สัมภาษณ์คุณ แล้วเขียนสเปก)

**เป้าหมาย:** กติกาของระบบเขียนเป็นเอกสารที่ละเอียดพอให้ใครก็ implement ได้เหมือนกัน โดยไม่ต้องถามใคร
**เวลา:** 45 นาที · **ก่อนหน้า:** [Step 1](01-plan-with-ai.md) · **ถัดไป:** [Step 3](03-openapi.md)

## หลักคิด

สเปกคือสิ่งที่ทุกภาษายึดเป็นตัวตัดสิน ถ้าสเปกกำกวม AI แต่ละรอบ (และแต่ละภาษา) จะเลือกคำตอบต่างกัน แล้วคุณจะเห็นเป็น "bug" ตอนแปล ทั้งที่ต้นเหตุคือสเปก

มี 2 ไฟล์:

| ไฟล์ | เนื้อหา |
|---|---|
| `spec/evaluation.md` | **สมอง** ของระบบ: ลำดับการประเมิน flag, targeting, rollout, การเลือก variant, อัลกอริทึม hash แบบละเอียดถึงระดับไบต์ |
| `spec/business-rules.md` | กฎอื่นๆ ที่มี ID (`BR-01`, `BR-02`…): validation, auth, audit, รูปแบบ error ฯลฯ |

## ขั้นตอน

### 2.1 ให้ AI สัมภาษณ์คุณ (ไม่ใช่ให้ AI เดา)

```text
ฉันต้องการเขียนสเปกการประเมิน feature flag ที่รองรับ: on/off, targeting rule, rollout เป็น %,
และ A/B variants ที่ user คนเดิมต้องได้ผลเดิมเสมอ (deterministic) และทุกภาษาต้องคำนวณได้เท่ากัน

สัมภาษณ์ฉันทีละ 1 คำถาม หัวข้อที่ต้องครอบคลุม:
ลำดับการประเมิน, ค่า/attribute ที่ไม่มี, การเทียบชนิดข้อมูล ("1" กับ 1), การ bucket ด้วย hash,
user ที่ไม่มี id, ลำดับของ variants, การตรวจ request
แต่ละคำถามให้ตัวเลือก 2-3 ข้อ พร้อมข้อดีข้อเสีย และบอกข้อที่แนะนำ
เมื่อครบ 12 คำถามให้สรุปเป็นรายการ decisions แล้วหยุดรอฉันยืนยัน ห้ามเขียนไฟล์
```

ตอบทีละข้อ สิ่งที่ควรตัดสินใจให้ชัด (ตัวอย่างคำตอบที่ใช้ในรีโปนี้):

| หัวข้อ | ตัดสินใจ |
|---|---|
| attribute ที่ไม่มีใน context | rule ไม่ผ่านทุก operator (รวม `neq`, `not_in`) |
| เทียบชนิด | เข้มงวด: `"1" ≠ 1`, `true ≠ "true"` |
| hash | FNV-1a 32-bit บนไบต์ UTF-8 (สั้น เขียนซ้ำง่าย ไม่ต้องพึ่ง library) |
| bucket | `fnv1a32(flagKey:salt:userId) mod 10000` แยก salt `rollout`/`variant` เพื่อไม่ให้ทั้งสองสัมพันธ์กัน |
| ไม่มี userId แต่ต้อง bucket | ผลเป็น `MISSING_USER_ID` ไม่เดา |
| ลำดับ variants | มีผลต่อการเลือก ต้องคงตามที่ประกาศ |

### 2.2 ให้ AI เขียนสเปกจาก decisions

```text
จาก decisions ที่ยืนยันแล้ว เขียน 2 ไฟล์ (ภาษาไทย ศัพท์เทคนิคภาษาอังกฤษ):

1. spec/evaluation.md
   - ตาราง flag model และ reason ทั้งหมด
   - ลำดับการประเมินเป็นข้อๆ พร้อมระบุว่า "ห้ามสลับ"
   - อัลกอริทึม hash เป็น pseudo-code ที่ระบุ: ค่าเริ่มต้น, prime, การ wrap 32 บิต, ว่า hash บนไบต์ UTF-8
   - ทุกกฎมีตัวอย่างที่เป็นตัวเลขจริง (เช่น rollout 10% = bucket 0..999)
2. spec/business-rules.md
   - ตารางกฎ ทุกข้อมี ID BR-xx, กฎ, และผลเมื่อฝ่าฝืน (HTTP status + error code)
   - แยกกลุ่ม MVP1 / MVP2

ห้ามเพิ่มกฎที่ฉันไม่ได้ตัดสินใจ ถ้าต้องการกฎเพิ่มให้ถามก่อน
```

### 2.3 ให้ AI หาจุดกำกวมในสเปกของตัวเอง (ขั้นที่คนมักข้าม แต่ได้ผลที่สุด)

เปิดบทสนทนาใหม่ (เพื่อให้ AI ไม่ลำเอียงกับสิ่งที่เพิ่งเขียน):

```text
อ่าน spec/ ทั้งหมดในฐานะ dev ที่ต้อง implement ด้วย Rust โดยไม่มีใครให้ถาม
ลิสต์ "ทุกจุด" ที่ตีความได้มากกว่า 1 แบบ ไม่ใช่แค่ 5 ข้อ พร้อม:
- คำตอบที่แนะนำ
- test case 1 ข้อที่จะชี้ขาดว่า implementation ตีความถูกหรือผิด
เรียงจากจุดที่ถ้าตีความผิดจะกระทบมากที่สุดไปน้อยสุด
```

ตัดสินใจทีละข้อ แล้วสั่ง AI อัปเดตสเปก

> **บทเรียนจากการทำจริง:** ในรีโปนี้เราข้ามขั้น 2.3 แล้วไปเจอจุดกำกวมตอนเขียน contract test (step 5) เช่น PUT เป็น replace หรือ merge, `before/after` ใน audit log เป็นอย่างไร, สูตร z-test, ลำดับตรวจ auth → validation → 404/409 ต้องย้อนกลับมาแก้สเปก ถ้าทำ 2.3 ตั้งแต่ตอนนี้จะประหยัดการย้อนกลับ

```bash
git add -A && git commit -m "Add evaluation spec and business rules"
```

## ตรวจผล (เช็กลิสต์ ไม่มีคำสั่งอัตโนมัติ)

```bash
grep -oE "^\| BR-[0-9]+" spec/business-rules.md | sort | uniq -d   # ต้องไม่มี ID ซ้ำ (ไม่ขึ้นอะไรเลย)
grep -cE "^\| BR-[0-9]+" spec/business-rules.md                    # จำนวนกฎที่ประกาศ (เฉลย: 33)
```

- [ ] ทุกกฎใน `business-rules.md` มี ID และผลเมื่อฝ่าฝืน (status + code)
- [ ] `evaluation.md` มี **ตัวอย่างตัวเลข** อย่างน้อย 1 ตัวอย่างต่อกฎ
- [ ] อัลกอริทึม hash เขียนถึงระดับที่คนเขียนโค้ดได้โดยไม่ต้องเดา (ค่าเริ่มต้น, prime, ไบต์ UTF-8, wrap 32 บิต)
- [ ] ไม่มีคำว่า "ตามความเหมาะสม", "ปกติ", "อาจจะ" ในส่วนที่เป็นกติกา
- [ ] ทำ 2.3 แล้ว และทุกจุดกำกวมมีคำตอบในสเปก

## ข้อควรระวัง

- ถ้า AI ถามหลายข้อพร้อมกัน ให้สั่ง "ถามทีละข้อ" ไม่งั้นคุณจะตอบผ่านๆ
- สเปกที่ AI เขียนมักอ่านดูครบ แต่ **ตัวอย่างตัวเลขมักผิด** ให้คำนวณด้วยมือหรือด้วยโค้ดอย่างน้อย 2 ตัวอย่าง (step 4 จะตรวจให้ทั้งหมดอีกชั้น)
- ใช้คำเดียวกันตลอดทั้งสเปก (`flag`, `variant`, `bucket`) AI จะสับสนถ้าคำเดียวกันมีหลายความหมาย
